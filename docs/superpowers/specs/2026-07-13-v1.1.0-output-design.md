# v1.1.0 — Output Teams Can Use: Design Spec

**Date:** 2026-07-13
**Status:** Approved (design review complete; pending implementation plan)
**Release target:** 1.1.0
**Roadmap context:** Phase 1 of the relaunch plan ("Output That Teams Can Use"). This release unblocks Phase 2 (`diff --base main`, v1.2.0), Phase 3 (baseline/ratchet, v1.3.0), and Phase 4 (GitHub Action, v1.4.0), all of which consume the structured output introduced here.

## Problem

pycleancode 1.0.4 prints human-oriented text to stdout and always exits 0. Teams cannot:

- fail a CI build on violations (no meaningful exit code),
- consume results programmatically (no JSON),
- post results to a pull request (no Markdown),
- configure the tool from `pyproject.toml` (YAML file only),
- run the tool without a `pybrace.yml` present (missing config crashes with `FileNotFoundError` — the docs quickstart fails on a fresh install).

Additionally, the CLI entry point `pycleancode-brace-linter` is module-scoped, while the roadmap and marketing standardize on `pycleancode check`.

## Decisions (locked during design review)

1. **CLI:** new unified `pycleancode` entry point with a `check` subcommand. `pycleancode-brace-linter` remains as a deprecated alias that forwards to `check` and prints one deprecation notice to stderr. Removal targeted for 2.0.
2. **Exit codes:** severity-aware, CI-standard. `0` = clean or warnings-only; `1` = at least one error-severity violation; `2` = usage/config/parse/write failure. Violations carry a severity (`error` | `warning`); rules default to `error`; config may downgrade a rule via `severity: warning`.
3. **Config:** layered discovery. Explicit `--config <path>` (error if absent) → `./pybrace.yml` → `[tool.pycleancode]` in `./pyproject.toml` → built-in defaults (both rules enabled, `max_depth: 3`, `max_nested: 1`, severity `error`). Fixes the no-config crash.
4. **Formats:** `text` (default, preserves current console behavior), `json` (with `schemaVersion`), `markdown`. Selected via `--format`, written to stdout or to `--output <file>`. SARIF explicitly deferred.
5. **Refactor scope: full hygiene sweep.** Analyzer returns structured results; `RuleViolation` gains `rule_name` and `severity`; dead `reporter/formatter.py` is absorbed/deleted; unused `parser/parser_engine.py` and its tests are deleted; `test_rule_registry.py` is rewritten to stop writing `dummy_rule.py` into the production rules package.

## Architecture

Principle: **the analyzer produces data; the CLI layer decides presentation and exit code.**

```
pycleancode/
  cli.py                      NEW  root Typer app: `pycleancode` (check, --version)
  core/
    config.py                 ConfigLoader kept + NEW ConfigResolver (layered discovery)
  brace_linter/
    cli.py                    thin deprecated shim -> forwards to root CLI `check`
    analyzer.py               returns AnalysisRun; no print() calls remain
    output/                   NEW  formatter package
      base.py                 OutputFormatter protocol
      text_formatter.py       current console output (tree/summary/chart under --report)
      json_formatter.py       schemaVersion-stamped machine output
      markdown_formatter.py   PR-comment-ready summary
    rules/
      violation_model.py      RuleViolation + rule_name + severity
      rule_engine.py          stamps rule_name/severity onto violations
    reports/                  kept; tree models feed the text formatter
    parser/                   DELETED (unused ParserEngine)
    reporter/                 DELETED (dead formatter.py absorbed by output/)
```

Dependency direction is unchanged: `cli -> analyzer -> loaders/rules/output -> models`. Formatters depend only on the result models.

### Severity stamping

Rules stay pure (no printing, no config access — the rule-extension contract is unchanged). `RuleLoader` builds a `{rule_name: severity}` map from config, defaulting to `error`. `RuleEngine` stamps `rule_name` and `severity` onto each violation as it collects results. The `severity` key is stripped alongside `enabled` before rule construction, preserving the constructor contract fixed in 1.0.3.

## Data model

```python
Severity = Literal["error", "warning"]

@dataclass
class RuleViolation:              # rules/violation_model.py (extended)
    file_path: str
    line_number: int
    message: str
    rule_name: str = ""
    severity: Severity = "error"

@dataclass
class FileResult:
    file_path: str
    violations: list[RuleViolation]
    summary: FileSummary
    structure: NodeReport | None  # populated only when --report

@dataclass
class AnalysisRun:
    results: list[FileResult]
    # computed properties: error_count, warning_count, files_analyzed
```

`BraceLinterAnalyzer.analyze()` returns an `AnalysisRun`. Every formatter consumes this object; exit-code logic reads its counts; the JSON format is essentially this model serialized.

## CLI contract

```
pycleancode check PATH [--config FILE] [--format text|json|markdown]
                        [--output FILE] [--report]
pycleancode --version
```

- `--format` defaults to `text`. Without `--output`, all formats write to stdout; with it, to the file.
- `--report` retains its current meaning (structure tree) and affects only the `text` format. JSON and Markdown always embed per-file summaries.
- `pycleancode-brace-linter <path> [--config] [--report]` keeps its exact 1.0.x argument shape, prints one deprecation notice to **stderr** (never corrupting piped stdout), and forwards to `check`.

### Exit codes

| Code | Meaning |
|------|---------|
| 0 | No violations, or warnings only |
| 1 | At least one error-severity violation |
| 2 | Usage/config error, unparseable source file, or output-write failure |

Exit codes are computed in `cli.py` from the `AnalysisRun`; the analyzer never calls `sys.exit`.

### JSON output (schemaVersion 1)

```json
{
  "schemaVersion": 1,
  "summary": {"files": 12, "errors": 3, "warnings": 1},
  "violations": [
    {"file": "src/orders.py", "line": 5, "rule": "max_depth",
     "severity": "error", "message": "Depth 4 exceeds max 3"}
  ]
}
```

The schema is a compatibility promise: additive changes only within schemaVersion 1; breaking changes increment it. The v1.4.0 GitHub Action will consume this format.

### Markdown output

A PR-comment-ready summary: run totals, then a table of violations (file, line, rule, severity, message). Exact layout is an implementation detail validated by golden-file tests, not a compatibility promise in 1.1.0.

## Config resolution

`ConfigResolver` in `core/config.py`, checked in order:

1. `--config <path>` — missing or unreadable file is an error (exit 2).
2. `./pybrace.yml`
3. `[tool.pycleancode]` in `./pyproject.toml`
4. Built-in defaults: both rules enabled, `max_depth: 3`, `max_nested: 1`, severity `error`.

TOML is normalized to the same dict shape YAML produces; `RuleLoader` is source-agnostic. Example:

```toml
[tool.pycleancode.rules.max_depth]
enabled = true
max_depth = 3
severity = "warning"
```

**New dependency:** `tomli >= 2` for Python < 3.11 only (`tomllib` is stdlib from 3.11). This is the release's entire new dependency footprint.

## Error handling

- Missing/invalid `--config`, malformed YAML/TOML, nonexistent target path: one-line message to stderr, exit 2.
- Unparseable source file (LibCST failure): analysis continues for remaining files; the failure is reported in output; the run exits 2.
- `--output` write failure: exit 2.
- All user-facing paths continue to pass through `sanitize_console_text` before printing.

## Testing

- **Unit:** ConfigResolver precedence matrix (all four layers; tomli/tomllib across 3.9–3.12); golden-file tests for JSON (locks the schema) and Markdown; exit-code computation table; RuleEngine severity/rule-name stamping; deprecation shim behavior.
- **Integration:** Typer `CliRunner` end-to-end — `check` command, old alias (deprecation on stderr, same results), `--format`/`--output` combinations, exit 0/1/2 scenarios.
- **Hygiene:** delete `parser/` tests with the module; rewrite `test_rule_registry.py` to create rule files in `tmp_path` instead of the production package.
- Coverage, mypy, black, ruff gates unchanged.

## Out of scope

SARIF output, diff/regression mode, baseline files, GitHub Action, PR comments, new rules. Docs-site and README/CHANGELOG updates happen in the release cycle, outside this spec's implementation plan.

## Migration notes for users

- `pycleancode-brace-linter` keeps working through all 1.x releases; scripts should migrate to `pycleancode check`.
- Runs that previously exited 0 despite violations will now exit 1 in CI once upgraded — this is the feature. Teams that want report-only behavior set `severity: warning` on rules during adoption.
